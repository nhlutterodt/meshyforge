## 2. Why this run is different

Every prior verification in this repository is mock-based. The Rust suite uses
`wiremock`; the frontend's 492 tests mock `@tauri-apps/api/core`. As a result
**no test had ever crossed the real IPC boundary**. Three consequences were known
and are now addressed or quantified:

- `validate_download_url` restricts downloads to `https://assets.meshy.ai`, so
  the real download path was never executed — only its rejection path.
- Tauri v2 converts Rust `snake_case` command parameters to `camelCase` in the
  webview. A parameter-name mismatch is invisible to every existing test and
  would silently break only one code path.
- `convertFileSrc` + the CSP `asset:` scope were exercised exclusively against mocks.

This run drives the real boundary instead.

Two facts here are load-bearing:

1. **A 70 MB database with 4.55 GB behind it is a real migration target.**
   `Database::open` runs migrations eagerly, so launching the app against this
   database is the only way to prove migration 003 applies safely in place — and
   the only thing that exercises the `backup_recovery` schema-mismatch risk on
   real data. It did. (§7.1)
2. **168–195 MB `.obj` files corroborate P-10.** The pre-fix download path used
   `response.bytes().await?`, buffering the whole body in memory. On this library
   that is a genuine ~200 MB single allocation per download, not a hypothetical.

A byte-level backup of the database (and `-shm`) was taken before the first
launch, and all mutated rows were restored afterwards (§9).

## 4. ENV-01 — the application could not start (root-caused)

The first launch attempt failed with:

```
[tauri_runtime_wry][ERROR] Could not find the webview runtime, make sure it is installed
```

The process started, logged from `keyring`, never opened a window, spawned no
WebView2 child processes, and hung. This is **not** an application defect. The
diagnosis:

| Check | Result |
|---|---|
| `HKLM\...\EdgeUpdate\Clients\{F3017226-…}` | `pv = 157.0.4341.42`, location present — runtime registered |
| Version folder | 918 files / 878 MB, `msedgewebview2.exe` present, `EBWebView\x64\EmbeddedBrowserWebView.dll` present |
| **`WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` (User scope)** | **`…\EdgeWebView\Application\156.0.4314.50` — a folder that no longer exists** |

The runtime auto-updated from **156.0.4314.50 → 157.0.4341.42 on 2026-11-07**,
leaving a stale per-user override pointing at the deleted version directory. The
WebView2 loader honours that override and fails instead of falling back to the
registered Evergreen install.

**Remedy (environment, not code):**

```powershell
[Environment]::SetEnvironmentVariable('WEBVIEW2_BROWSER_EXECUTABLE_FOLDER', $null, 'User')
```

Clearing it for the launching process alone was sufficient to start the app
(window "MeshyForge", 6 WebView2 children, CDP on port 9333).

> Worth recording because it is a *support* trap: a non-technical user hitting
> this sees a silently dead app with no dialog. It is not covered by any repo
> document.

## 6. QA-01 — navigation dead-end while an asset is open (found, fixed, re-verified)

### 6.1 Observed

| Scenario | Observed | Expected |
|---|---|---|
| A. Grid → sidebar `Gallery` | stays on grid | stays on grid ✔ |
| B. **Detail → sidebar `Gallery`** | **stays on the detail view** — grid unreachable | show the grid |
| C. **Detail → `Tasks` → `Gallery`** | **silently re-opens the previously selected asset** | show the grid |
| D. Detail → `Back to Gallery` | returns to grid | returns to grid ✔ |

The sidebar `Gallery` item appears selected and is unresponsive. During
scenario B the sidebar visually highlights `Gallery` while the page shows the
asset detail, so the UI also *lies about its own location*.

This was observed twice in the run (once while mapping the gallery, once at the
end of a journey), and reproduced deterministically in the dedicated
characterisation pass — it is not flakiness.

### 6.2 Root cause

`src/app/routes.tsx:131`

```tsx
case 'gallery':
  return selectedAssetId ? (
    <AssetDetail assetId={selectedAssetId} onBack={() => setSelectedAsset(null)} />
  ) : ( /* gallery grid */ );
```

`setActiveView` only wrote `activeView`:

```ts
setActiveView: (view) => set({ activeView: view }),
```

The gallery's *position* is therefore a composite of two store fields
(`activeView`, `selectedAssetId`), while navigation only ever writes one. Two
consequences follow directly:

- **B** — `activeView` is already `'gallery'`, so switching to `'gallery'`
  changes nothing at all and the detail panel persists.
- **C** — leaving to `Tasks` changes `activeView` but leaves `selectedAssetId`
  set, so returning to `gallery` re-enters the detail branch.

The same flaw existed on the keyboard path: `useKeyboardShortcuts` set
`selectedAssetId` to `null` only for the `Delete` key, and Ctrl/Cmd+K set
`activeView('gallery')` without clearing the selection.

### 6.3 Fix (red-first)

`src/stores/appStore.ts` — navigating anywhere now dismisses an open detail:

```ts
setActiveView: (view) => set({ activeView: view, selectedAssetId: null }),
```

Three regression tests were added to `src/stores/appStore.test.ts` and **failed
first** (`expected 'task-42' to be null`), then passed:

1. `clears the selected asset when navigating to gallery`
2. `clears the selected asset when navigating to any other view`
3. `leaves the selected asset alone when re-entering the same non-gallery view`

The fix is 1 line of production code. It is deliberately placed in the store
rather than per-caller because `setActiveView` has multiple callers (Sidebar,
keyboard shortcuts), and the invariant "navigation ends any open detail" belongs
to the navigation action.

### 6.4 Re-verification against the running application

Rebuilt and reloaded the real app, then re-ran the same scenarios:
**10/10 checks passed.** Scenarios B and C now both show the grid;
`Back to Gallery`, the detail view, the live WebGL context, search, and the full
`Tasks`/`Settings`/`Generate`/`Gallery` round trip all still work, with 0 console errors.

## 7. Findings from the prior audit — confirmed or bounded by this run

### 7.1 P-01 / migration 003 — **confirmed effective on real data**

After one launch, the real database reported `schema_version = 3` with versions
`[1, 2, 3]` present, and the composite index exists. The plan for the real paged
query is:

```
SCAN assets USING INDEX idx_assets_created_id
```

**No `USE TEMP B-TREE`** — the regression P-01 described is absent under the
shipping `SELECT *` query. Paging integrity was also confirmed over the real IPC
boundary: `limit=5` at offsets `0/5/10/13` returned `5/5/3/0` rows, `total=13`,
and **zero id overlap between consecutive pages** — exactly 13 distinct ids
across 4 pages. This is the first time the paging contract has been proven
end-to-end rather than in-process.

Eager migration of a real 70 MB database also completed cleanly, which bounds
the `backup_recovery` risk noted when migration 003 was introduced.

### 7.2 P-03 — **confirmed live in the running UI**

The status bar renders **"0 assets"** while the gallery simultaneously displays
13 cards (visible together in one screenshot). `StatusBar.tsx:17` hardcodes
`const storageUsage = 0`, and `get_storage_usage` returns `13` — a row *count*,
not the byte total `FR-EXP-05-F1` specifies. Pre-existing; unchanged by this
work. Both halves of P-03 now have direct runtime evidence.

### 7.3 P-10 — **risk evidence strengthened**

The 168–195 MB `.obj` files in the real library mean the removed
`response.bytes().await?` path was allocating ~200 MB per download on this
machine's own data. The streaming + 2 GiB cap change is justified by this
library, not by theory.

### 7.4 P-02 — **not exercisable here (bounded)**

Load More / `fetchNextPage` cannot fire with 13 assets against a 50-row page
size. The pagination *contract* was verified at the IPC level (§7.1), but the
button's *UI* path remains unproven. Deliberately **not** forced by inserting 50
synthetic rows into the user's real library.

## 10. What this run does **not** cover

Stated explicitly so the pass in §5 is not over-read.

1. **Generation, upload, and download flows.** These require a live Meshy API key
   and consume billable credits. Secrets must not be routed through the model, so
   these are structurally out of reach of an automated run; they need either the
   owner driving them or a key supplied outside this channel. The gallery here
   contains assets from earlier manual sessions, not from this run.
2. **Load More in the UI** (§7.4) — the library is smaller than one page.
3. **Visual / pixel-level regression.** Assertions cover DOM state, WebGL context
   health, HTTP status, and a screenshot reviewed by eye. There is no
   perceptual-diff baseline.
4. **Destructive and OS-integrated actions**: Delete (no undo), Export (file
   dialog), Reveal (OS file manager), plus multi-window and native dialog behaviour.
5. **Packaging.** This is a debug build run from the Vite dev server. The
   `frontendDist`/`devUrl` resolution, installer, code-signing, and a clean-machine
   first run are untouched.
6. **Concurrency / streaming.** A single window, a single process, no in-flight
   tasks, and no SSE stream were exercised.
7. **Migration from a populated v2 database with tags present** — `tags` and
   `asset_tags` were empty (§3), so tag-carrying migration behaviour is unproven.

## 12. Reproduction recipe

```powershell
# 1. Clear the stale WebView2 override (ENV-01)
[Environment]::SetEnvironmentVariable('WEBVIEW2_BROWSER_EXECUTABLE_FOLDER', $null, 'User')

# 2. Back up real data
Copy-Item "$env:APPDATA\com.meshyforge.app\meshyforge.db" "$env:TEMP\meshyforge-qa-backup\meshyforge.db.bak"

# 3. Build and launch the app with a CDP endpoint
npm run build
cargo build --manifest-path src-tauri/Cargo.toml
$env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = '--remote-debugging-port=9333'
Start-Process 'src-tauri\target\debug\meshyforge.exe'

# 4. Attach Playwright (browsers already cached under %LOCALAPPDATA%\ms-playwright)
#    chromium.connectOverCDP('http://127.0.0.1:9333')
```

Notes for reuse:

- Port **9222** is commonly already held by the user's own Chrome; use another port.
- **Never call `browser.close()` on a CDP connection** — it can terminate the app.
  Any harness built from this must avoid it.
- Readiness must be polled (wait for `canvas` / `[class*="group/card"]`), because
  attaching does not imply the SPA has mounted.
- `@playwright/test` is **already** in `devDependencies`; no new dependency is
  required to repeat this run.

## 13. Recommendations

1. **Land QA-01** — committed on the current branch with red-first coverage.
2. **ENV-01** — clear the stale user-scope variable on this machine; consider a
   troubleshooting note, since the failure mode is a silently dead app.
3. **Make the gap durable.** This run found a defect that all 492 unit tests and
   374 Rust tests missed because none of them crosses the real IPC boundary and
   navigation was never asserted as a *composite* of store fields. Options, in
   increasing cost: (a) store- and routes-level tests for navigation invariants
   such as the three added here; (b) a committed CDP smoke harness covering
   launch → gallery → detail → WebGL → search, which is cheap now that the
   recipe is known.
4. **`get_api_key` naming** — rename or add a `has_api_key` alias (§8).
5. **P-03** — `StatusBar` still hardcodes `0`; both halves (byte-total semantics
   and the frontend consumer) remain open and are now confirmed live.
