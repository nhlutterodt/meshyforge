## 1. Purpose

The Documentation Gap Assessment (§6.3, Gap 4) evaluated whether a standalone "Complete Zustand Store Implementations" document was needed and recommended **against** generating it, on the grounds that `settingsStore.ts` was already fully specified as the canonical pattern reference in CSD §8.2, and that `appStore.ts` and `taskStore.ts` were "simpler" and adequately covered by their interface definitions in TDD §8.1.

This document is produced at the project owner's explicit request, overriding that recommendation. Its purpose is to collect the **complete, final, directly-usable** implementations of all three Zustand stores — `appStore.ts`, `taskStore.ts`, and `settingsStore.ts` — in one place, so an implementer can copy each store verbatim into `src/stores/` without cross-referencing multiple design documents.

Each store below is the target content of its corresponding file under `src/stores/`, written as a complete reference ahead of implementation. All three stores are written to comply with the state boundary rules in CSD §8.1 (STT-01 through STT-07):

- No imports from `@tanstack/react-query` (STT-05 / ORG-08) — server-derived data never lives here.
- No imports from `@tauri-apps/api` (STT-05 / ORG-08) — stores are pure state containers with no side-effecting platform calls.
- No React imports — these are plain Zustand stores consumed via hooks generated by `create()`, not components.
- State mutation happens only through named actions exposed on the store interface (STT-07); no component reaches into store internals directly.
- `appStore` and `taskStore` hold pure UI/ephemeral state (STT-02); `settingsStore` holds persisted user preferences (STT-03) and is the only one of the three wrapped in the `persist` middleware.

For `settingsStore.ts`, this document reproduces the CSD §8.2 reference implementation verbatim. **CSD §8.2 remains the source of truth for `settingsStore.ts`** — if the two ever diverge, CSD §8.2 wins and this document should be regenerated to match. `appStore.ts` and `taskStore.ts` are reproduced from TDD §8.1, which already contains complete implementations for both (including the full `taskStore` action bodies — `addTask`, `updateTask`, `removeTask`, `clearCompleted`); nothing was left partially implemented in the source. No functional additions were made beyond what TDD §8.1 and CSD §8.2 already specify — see §5 for the judgment calls made in assembling this reference.

## 2. appStore.ts

Owns transient navigation and UI-chrome state: which top-level view and Generate sub-tab is active, which asset is selected for the detail panel, and whether the sidebar is collapsed. None of this state is persisted or derived from the Meshy API — it resets to defaults on every app launch (STT-02).

```typescript
// src/stores/appStore.ts
import { create } from 'zustand';

interface AppState {
  // ── Navigation ──────────────────────
  activeView: 'generate' | 'gallery' | 'tasks' | 'settings';
  setActiveView: (view: AppState['activeView']) => void;

  // ── Generate sub-panel ───────────────
  activeGenerateTab:
    | 'text-to-3d' | 'image-to-3d' | 'multi-image'
    | 'post-process' | 'rigging' | 'animation'
    | 'image-gen' | 'print' | 'creative-lab';
  setActiveGenerateTab: (tab: AppState['activeGenerateTab']) => void;

  // ── Selected asset (for detail view) ─
  selectedAssetId: string | null;
  setSelectedAsset: (id: string | null) => void;

  // ── Sidebar collapsed ────────────────
  sidebarCollapsed: boolean;
  toggleSidebar: () => void;
}

export const useAppStore = create<AppState>((set) => ({
  activeView: 'generate',
  setActiveView: (view) => set({ activeView: view }),
  activeGenerateTab: 'text-to-3d',
  setActiveGenerateTab: (tab) => set({ activeGenerateTab: tab }),
  selectedAssetId: null,
  setSelectedAsset: (id) => set({ selectedAssetId: id }),
  sidebarCollapsed: false,
  toggleSidebar: () => set((s) => ({ sidebarCollapsed: !s.sidebarCollapsed })),
}));
```

### Usage notes
- Components read slices via selectors, e.g. `const activeView = useAppStore((s) => s.activeView);`, to avoid re-rendering on unrelated state changes.
- `selectedAssetId` is a UI pointer only — the actual `Asset` record it references is fetched from TanStack Query (e.g. `useAsset(selectedAssetId)`), never duplicated into this store (STT-01).
- This store is intentionally **not** wrapped in `persist` — navigation state resetting to `'generate'` on relaunch is the desired MVP behavior. If cross-session view memory is wanted post-MVP, wrap with `persist` following the `settingsStore` pattern in §4, but that is out of scope here.

## 3. taskStore.ts

Tracks in-flight Meshy API tasks (polling or SSE-streamed) for the Task Monitor UI. This is UI-facing progress state, not the source of truth for task history — completed task records are persisted to SQLite and read back through TanStack Query, per STT-01. `taskStore` only holds tasks that are actively being tracked in the current session.

```typescript
// src/stores/taskStore.ts
import { create } from 'zustand';

interface ActiveTask {
  taskId: string;
  endpoint: string;
  meshyType: string;
  status: 'PENDING' | 'IN_PROGRESS' | 'SUCCEEDED' | 'FAILED' | 'CANCELED';
  progress: number;
  label: string;             // Human-readable: "Text to 3D: a monster mask"
  startedAt: number;
  error: string | null;
}

interface TaskState {
  activeTasks: Map<string, ActiveTask>;
  addTask: (task: ActiveTask) => void;
  updateTask: (taskId: string, updates: Partial<ActiveTask>) => void;
  removeTask: (taskId: string) => void;
  clearCompleted: () => void;
}

export const useTaskStore = create<TaskState>((set) => ({
  activeTasks: new Map(),
  addTask: (task) => set((s) => {
    const tasks = new Map(s.activeTasks);
    tasks.set(task.taskId, task);
    return { activeTasks: tasks };
  }),
  updateTask: (taskId, updates) => set((s) => {
    const tasks = new Map(s.activeTasks);
    const existing = tasks.get(taskId);
    if (existing) {
      tasks.set(taskId, { ...existing, ...updates });
    }
    return { activeTasks: tasks };
  }),
  removeTask: (taskId) => set((s) => {
    const tasks = new Map(s.activeTasks);
    tasks.delete(taskId);
    return { activeTasks: tasks };
  }),
  clearCompleted: () => set((s) => {
    const tasks = new Map(s.activeTasks);
    for (const [id, task] of tasks) {
      if (['SUCCEEDED', 'FAILED', 'CANCELED'].includes(task.status)) {
        tasks.delete(id);
      }
    }
    return { activeTasks: tasks };
  }),
}));
```

### Usage notes
- `activeTasks` is a `Map<taskId, ActiveTask>` rather than an array so `updateTask` (called on every poll tick / SSE message) is O(1) instead of requiring an array scan — this matters given `maxConcurrentTasks` (see `settingsStore.maxConcurrentTasks`, default 5) tasks may all be updating on overlapping poll intervals.
- Each `set()` call above creates a **new** `Map` instance rather than mutating `s.activeTasks` in place. This is required for Zustand's shallow-equality change detection to fire — mutating the existing Map and returning the same reference would silently fail to trigger re-renders.
- The Tauri backend event listeners / TanStack Query mutation `onSuccess`/`onProgress` callbacks that drive `addTask` / `updateTask` / `removeTask` live in the query hook layer (TDD §8.2), not in this store — per STT-05/STT-06, this file must never import `@tauri-apps/api` or `@tanstack/react-query` itself, and TanStack Query hooks call these actions but this store never calls back into Query.
- `clearCompleted` is intended to be wired to a "Clear finished" button in the Task Monitor (UI/UX §9.4); it does not delete anything from SQLite — the persisted task log is untouched.

## 4. settingsStore.ts

Holds user preferences (default generation parameters, polling behavior, notification/download behavior) with `persist` middleware backing it to `localStorage`, which Tauri maps to the OS app-data directory (STT-03). This is the canonical Zustand pattern reference for the project — see CSD §8.2.

> **Source of truth:** This section reproduces CSD §8.2 verbatim for completeness of this reference document. If `settingsStore.ts` is ever modified, update CSD §8.2 first and regenerate this section to match — do not let the two drift.

```typescript
// src/stores/settingsStore.ts
// ─── Pattern: Zustand store with typed actions ────────────────
// The store interface defines both state and actions.
// Actions are the only way to mutate state.

import { create } from 'zustand';
import { persist } from 'zustand/middleware';
import type { AiModel, ExportFormat } from '../lib/meshy-types';

interface SettingsState {
  // ── State ──────────────────────────────────────
  readonly defaultAiModel: AiModel;
  readonly defaultTextureResolution: '2k' | '4k' | '8k';
  readonly defaultShouldRemesh: boolean;
  readonly defaultTargetPolycount: number;
  readonly defaultTargetFormats: readonly ExportFormat[];
  readonly defaultEnablePbr: boolean;
  readonly defaultRemoveLighting: boolean;
  readonly defaultPoseMode: string;
  readonly pollIntervalMs: number;
  readonly useSseStreaming: boolean;
  readonly maxConcurrentTasks: number;
  readonly autoDownloadOnSuccess: boolean;
  readonly notifyOnTaskComplete: boolean;

  // ── Actions ────────────────────────────────────
  setDefaultAiModel: (model: AiModel) => void;
  setDefaultTextureResolution: (res: '2k' | '4k' | '8k') => void;
  setPollIntervalMs: (ms: number) => void;
  setUseSseStreaming: (enabled: boolean) => void;
  setAutoDownloadOnSuccess: (enabled: boolean) => void;
  setNotifyOnTaskComplete: (enabled: boolean) => void;
  resetToDefaults: () => void;
}

const DEFAULTS = {
  defaultAiModel: 'latest' as AiModel,
  defaultTextureResolution: '2k' as const,
  defaultShouldRemesh: false,
  defaultTargetPolycount: 30000,
  defaultTargetFormats: ['glb', 'fbx'] as const,
  defaultEnablePbr: true,
  defaultRemoveLighting: true,
  defaultPoseMode: '',
  pollIntervalMs: 5000,
  useSseStreaming: false,
  maxConcurrentTasks: 5,
  autoDownloadOnSuccess: true,
  notifyOnTaskComplete: true,
} satisfies Omit<SettingsState, 'setDefaultAiModel' | 'setDefaultTextureResolution' | 'setPollIntervalMs' | 'setUseSseStreaming' | 'setAutoDownloadOnSuccess' | 'setNotifyOnTaskComplete' | 'resetToDefaults'>;

export const useSettingsStore = create<SettingsState>()(
  persist(
    (set) => ({
      ...DEFAULTS,

      setDefaultAiModel: (model) =>
        set({ defaultAiModel: model }),

      setDefaultTextureResolution: (res) =>
        set({ defaultTextureResolution: res }),

      setPollIntervalMs: (ms) =>
        set({ pollIntervalMs: Math.max(1000, Math.min(60000, ms)) }),

      setUseSseStreaming: (enabled) =>
        set({ useSseStreaming: enabled }),

      setAutoDownloadOnSuccess: (enabled) =>
        set({ autoDownloadOnSuccess: enabled }),

      setNotifyOnTaskComplete: (enabled) =>
        set({ notifyOnTaskComplete: enabled }),

      resetToDefaults: () =>
        set(DEFAULTS),
    }),
    {
      name: 'meshyforge-settings',
      version: 1,
      // Only persist user-modifiable settings, not computed defaults
      partialize: (state) => ({
        defaultAiModel: state.defaultAiModel,
        defaultTextureResolution: state.defaultTextureResolution,
        defaultShouldRemesh: state.defaultShouldRemesh,
        defaultTargetPolycount: state.defaultTargetPolycount,
        defaultTargetFormats: state.defaultTargetFormats,
        defaultEnablePbr: state.defaultEnablePbr,
        defaultRemoveLighting: state.defaultRemoveLighting,
        defaultPoseMode: state.defaultPoseMode,
        pollIntervalMs: state.pollIntervalMs,
        useSseStreaming: state.useSseStreaming,
        maxConcurrentTasks: state.maxConcurrentTasks,
        autoDownloadOnSuccess: state.autoDownloadOnSuccess,
        notifyOnTaskComplete: state.notifyOnTaskComplete,
      }),
    },
  ),
);
```

### Usage notes
- `AiModel` and `ExportFormat` are imported from `src/lib/meshy-types.ts` (TDD §6.2), where they are defined as `export type AiModel = 'meshy-5' | 'meshy-6' | 'meshy-7' | 'latest'` and `export type ExportFormat = 'glb' | 'fbx' | 'obj' | 'stl' | 'usdz' | '3mf'`.
- `partialize` deliberately re-lists every state field rather than destructuring away the action functions. This keeps the persisted payload explicit and stable across refactors — adding a new action to the store does not risk it accidentally leaking into `localStorage` through an automatic "everything that isn't a known action" filter.
- `version: 1` is reserved for future `migrate` functions if the persisted shape changes after release (Zustand's `persist` middleware calls `migrate(persistedState, version)` when the stored `version` is behind the store's declared version). No migration function is defined yet because there is no prior persisted version to migrate from.
- **Known asymmetry, preserved as-is from CSD §8.2:** the `SettingsState` interface exposes setter actions for only 6 of its 13 state fields (`defaultAiModel`, `defaultTextureResolution`, `pollIntervalMs`, `useSseStreaming`, `autoDownloadOnSuccess`, `notifyOnTaskComplete`). The remaining seven fields (`defaultShouldRemesh`, `defaultTargetPolycount`, `defaultTargetFormats`, `defaultEnablePbr`, `defaultRemoveLighting`, `defaultPoseMode`, `maxConcurrentTasks`) have no dedicated setter in the CSD §8.2 reference. This document reproduces that asymmetry unchanged rather than inventing additional setters, per the instruction to treat CSD §8.2 as canonical. See §5 for the judgment call this required.

## 5. Judgment Calls

This section documents the handful of decisions made while assembling this reference, since the source documents left them implicit.

1. **`appStore.ts` and `taskStore.ts` were already complete in TDD §8.1.** The task brief anticipated that `taskStore.ts` might be cut off mid-implementation in TDD §8.1 and asked for a careful forward-read to confirm. On inspection (TDD lines 1251–1343), both stores are fully implemented already, including the complete `taskStore` action bodies (`addTask`, `updateTask`, `removeTask`, `clearCompleted`). Nothing needed to be completed or inferred for either store — they are reproduced verbatim in §2 and §3.

2. **`settingsStore.ts`'s incomplete setter coverage was left as-is.** As noted in §4, seven of thirteen state fields in the CSD §8.2 reference lack a dedicated setter action. A tempting "completion" would be to add the missing seven setters (`setDefaultShouldRemesh`, `setDefaultTargetPolycount`, `setDefaultTargetFormats`, `setDefaultEnablePbr`, `setDefaultRemoveLighting`, `setDefaultPoseMode`, `setMaxConcurrentTasks`) for symmetry. This document does **not** do that, because the task brief was explicit that CSD §8.2 is canonical and should be reproduced, not redesigned. If full setter symmetry is wanted, that is a change to make in CSD §8.2 itself (with this document regenerated to match), not a divergence introduced here.

3. **Import path for `AiModel` / `ExportFormat`.** CSD §8.2's code fence uses these two types but does not show an import statement (the fence starts after a comment banner, not a `// src/stores/settingsStore.ts` file-path header like the other two stores). This document adds the missing `import type { AiModel, ExportFormat } from '../lib/meshy-types';` line, sourced from where TDD §6.2 defines both types (`src/lib/meshy-types.ts`), so the file in §4 is directly usable without the reader having to hunt down the import themselves.

4. **No `persist` middleware added to `appStore` or `taskStore`.** Per STT-02/STT-03, only user preferences are persisted — navigation state and in-flight task tracking are correctly ephemeral in the TDD §8.1 originals. A brief rationale note was added to each store's "Usage notes" (§2, §3) explaining why `persist` is absent, rather than silently leaving the reader to wonder if it was an oversight.

5. **No functional changes to any store's state shape, action signatures, or behavior.** This document is a compilation and completeness pass, not a redesign. Every field, action, and default value matches its source document exactly.
